## 登場人物

登場人物を順番に追うと:

1. **OBS → mediamtx（RTMP を受け取る）**
   OBS は「RTMP」という古くからある配信用プロトコルで映像を送ってきます。`mediamtx` は
   それを受け取る係です。受け取るだけでなく、**どの配信キーが今 publish（配信）中かを
   把握している**のが重要で、次のステップの引き金になります。

2. **mediamtx → ffmpeg（HLS に変換する）**
   VRChat が理解できる HLS 形式は、映像を「数秒ごとの小さいファイル（セグメント、`.ts`）」
   に切り分けて、「今どのファイルが再生可能か」を書いた目次ファイル（プレイリスト、
   `.m3u8`）を一緒に配る形式です。この切り分け作業をやるのが `ffmpeg` です。
   `mediamtx` は配信キーが有効になった瞬間に、**そのキー専用の `ffmpeg` を1つ起動**
   します（`on_available.sh` が実体）。配信が終わればその `ffmpeg` は自動的に止まり、
   複数のキーが同時に配信されれば `ffmpeg` もキーの数だけ並んで動きます。
   書き出された `.m3u8` と `.ts` は、コンテナ間で共有した RAM ディスク（tmpfs、`/hls`
   ボリューム）に置かれます。

3. **ffmpeg → nginx（配る）**
   `nginx` は `/hls` のファイルを HTTP で配るだけの、ごく普通の Web サーバです。ただし
   `.m3u8`（プレイリスト）は絶対にキャッシュさせず、`.ts`（セグメント）は逆に思い切り
   キャッシュさせています（[仕組みを詳しく](#仕組みを詳しくなぜこの設計か)で後述）。

4. **nginx → cloudflared → VRChat**
   `cloudflared` が自宅の外からアクセスできる HTTPS の URL を用意してくれます。VRChat の
   ワールドの動画URL欄にその URL（`https://.../<配信キー>/index.m3u8`）を貼ると、PC でも
   Quest でも同じ配信が見られます。

## 仕組みを詳しく（なぜこの設計か）

### なぜ mediamtx と nginx の2つだけなのか

以前はもう1つ `transcoder` という専用コンテナがあり、`ffprobe` で「配信キーが来ているか」を
3秒おきに確認し続ける、という作りでした。これは配信キーが `origin` に固定されていた頃の
設計です。

キーを OBS 側で自由に決められるようにした時点で、「どのキーを待ち受ければいいか」が
実行時にならないと分からなくなり、ポーリング前提の作りが成立しなくなりました。

MediaMTX には `runOnAvailable` / `runOnUnavailable` という path 単位のフックがあります。
**そのキーの配信が実際に読み取り可能になった瞬間にコマンドを起動し、配信が終わった瞬間に
SIGINT で止めてくれます。** どのキーが今アクティブかを MediaMTX 自身が正確に把握している
ので、別プロセスでポーリングして推測する必要がありません。キーごとに別プロセスが立つので、
複数キーの同時配信もこれだけで自然に並列動作します。

これを使うために `bluenviron/mediamtx` イメージを `-ffmpeg` タグ（ffmpeg 同梱・shell
あり）に切り替え、`transcoder` という別コンテナは廃止しました。フック1本が実質的に旧
`run.sh` の役割（入力検査 → ffmpeg 起動 → 終了処理）を担っています。中身の検査ロジック
自体は変えていません。

**配信キーの文字種を制限しているのは安全側の設計です。** `MTX_PATH`（＝配信キー）は
文字列としてそのまま `/hls/<キー>/` のようなパス組み立てに使われます。MediaMTX の path
設定を正規表現 `~^[A-Za-z0-9_-]{6,32}$` にしているので、これに一致しないキーはフックに
すら渡らず、パストラバーサル（`../` など）やシェルに解釈させたくない文字が紛れ込む余地が
ありません（フック側の環境変数受け渡しはシェル文字列への展開ではなく OS の環境変数として
渡る仕組みですが、念のためスクリプト側でも同じ形式を再検査しています）。

**二重配信を拒否している (`overridePublisher: no`) 理由。** 「部屋」に他人が割り込めて
はいけないので、同じキーへの2本目の publish は問答無用で拒否します。代償は自分自身の
瞬断再接続も `readTimeout` 分待たされることですが、乗っ取り防止のほうを優先しています。

### 遅延と安定性は別の軸で、旧構成はそれを分離できなかった

HLS プレイヤーの挙動を決めるのは、実は2つの別々のものです。

- **プレイリストに何本載っているか** → プレイヤーがどこから再生を始めるか → **遅延**
- **ディスクに何本残っているか** → 出遅れたクライアントがまだ取得できるか → **安定性**

MediaMTX の HLS マキサーは、この2つを `hlsSegmentCount` という**1つの数**で
まとめて扱います。RAM のリングバッファなので、プレイリストから溢れた瞬間に
実体も消えます。旧構成は `1秒 × 7本` だったので、

> プレイリストに 7 秒ぶん載っていて、**7 秒より古いものは存在しない**

という状態でした。猶予がゼロです。Quest の起動時バッファリング（PC より
1〜3 秒遅い）、Cloudflare エッジの往復、OBS の GOP のわずかな揺れ。
このどれかが重なって 7 秒の窓を踏み外した瞬間に 404 で死にます。
同じ URL・同じ設定なのに 18 秒差で成否が割れたのはこれが理由です。

ffmpeg の HLS マキサーはこの2つを別の設定として持っています。

| | ffmpeg | MediaMTX |
|---|---|---|
| プレイリストに載せる本数 | `hls_list_size` | `hlsSegmentCount` |
| 外した後も残す本数 | `hls_delete_threshold` | **無い** |

`hls_delete_threshold` に残ったセグメントは**プレイリストに現れません**。
だから遅延には 1ms も影響せず、出遅れたクライアントを救うためだけに存在します。
これが MediaMTX から ffmpeg に載せ替えた唯一にして最大の理由です。

現在の既定値は `窓 8 秒 / 猶予 60 秒`。遅延は旧構成と同じまま、
安全余裕だけが約 10 倍になっています。

### HLS はなぜ遅延がゼロにならないのか

配信映像を見るとき、必ず数秒の遅延があります。「サーバをもっと速くすれば消せるのでは」と
思うかもしれませんが、これは HLS という配信方式の仕組みそのものに起因する、避けられない
遅延です。

プレイヤー（VRChat）はまず目次ファイル（`.m3u8`）を取りに行き、目次に書かれている
「一番新しいファイルたち」のうち、**少し前のもの**から再生を始めます。一番新しいファイル
を狙うと、そのファイルがまだ書き終わっていなかったりネットワークの遅れで届いていなかったり
して再生が引っかかる（バッファリングする）リスクが高いからです。標準的な実装では、
**目次の一番新しいセグメントから3つ分だけ遡った位置**から再生を始めます。

```
OBS のエンコードと送出           0.3〜0.8s
セグメント1本の完成待ち          最大 1.0s
nginx + Cloudflare Tunnel        0.05〜0.2s
プレイヤーのライブエッジ戻し     3.0s   ← 3 × EXT-X-TARGETDURATION
                                ─────────
                                 約 4〜5s
```

`EXT-X-TARGETDURATION`（プレイリストに書く目次の単位）は仕様上**整数秒**なので、
1 秒セグメントでもライブエッジ戻しは 3 秒。セグメントを0.5秒にしても切り上げられて
1秒扱いになるため、この 3 秒という数字は変わりません（[調べ尽くした行き止まり](#調べ尽くした行き止まり)参照）。**このスタックの遅延設定は、理論上の下限にほぼ張り付いています。**
残る削りどころは OBS 側だけです（`tune=zerolatency`、NVENC なら P1〜P3 と
Look-ahead オフ、あと「配信の遅延」が有効になっていないか）。

ただし**削る前に測ることを勧めます。** 上の数字はプレイヤーが RFC どおりに
振る舞う前提の計算値で、AVPro が実際にどれだけ積むかは測らないと分かりません。
OBS のシーンにミリ秒表示の時計を出し、PC と Quest で同時再生して、
両方の画面を1枚の写真に収める。これで**両者のズレ**も同時に取れます。
同時視聴が目的である以上、絶対遅延よりそちらのほうが重要です。

その時計用に `https://<トンネルのホスト名>/clock` を用意してあります。
OBS のシーンにブラウザソースとして追加するだけで、配信映像にミリ秒表示の
時計が焼き込まれます。自分で時計素材を用意する必要はありません。

## 用語集

| 用語 | 意味 |
|---|---|
| RTMP | OBS が配信データを送るときに使う古典的なプロトコル。1本の映像ストリームを流し続ける方式 |
| HLS | 映像を数秒ごとの小さいファイルに切り分けて配る方式。VRChat の動画プレイヤーが対応している唯一の形式 |
| セグメント | HLS で切り分けられた映像の断片ファイル（`.ts`）。このスタックでは1本＝1秒 |
| プレイリスト / 目次ファイル | 「今どのセグメントが再生可能か」を書いたテキストファイル（`.m3u8`） |
| ライブエッジ | 配信の「今、この瞬間」に一番近い位置。プレイヤーはここから少し遅れた位置から再生する |
| キーフレーム / GOP | 映像圧縮の基準になるフレーム。HLSのセグメントはキーフレームの位置でしか切れないので、OBS側のキーフレーム間隔とセグメント長を一致させる必要がある |
| tmpfs | メモリ上に作られる一時的なディスク領域（RAMディスク）。セグメントファイルの置き場所として使っている |
| 配信キー / 部屋 | OBS の「ストリームキー」欄に入れる文字列。事実上、視聴URLの合言葉 |
| publish / publisher | OBS がサーバに向けて配信データを送っている状態、またはその送信元 |
